# 配置驱动的三版本校园人设测试设计

## 1. 目标

在不破坏大学版现有视觉与答题体验的前提下，将高中版、大学版、硕博版接入同一个应用。三版共用页面、状态管理、提交协议和判定引擎，题目、标签、结果、分享文案、四维指标、彩蛋及可调整算法规则均由配置提供。

完成后应满足：

- 身份页同时开放高中、大学、硕博三个入口；
- 三版均能完成 20 题、提交、生成结果、查看彩蛋和分享；
- 页面不硬编码任何具体题目、标签或版本专属结果；
- 修改题库或可配置算法参数时，不需要修改前端业务代码；
- 大学版现有可用行为保持兼容；
- 本地浏览器预览与云函数使用同一套数据协议；
- 第 20 题不能单独决定主标签。

## 2. 非目标

- 本阶段不重做大学版视觉系统；
- 不引入外部服务、数据库迁移或新的运行时依赖；
- 不提供可视化后台编辑器，题库仍通过受版本控制的 JSON/Markdown 和构建命令维护；
- 不把私有权重、核心题映射或完整判定规则下发给前端。

## 3. 当前差距

三套规范化题库已位于 `data/banks/`，并能通过统一校验。当前产品层仍只支持大学版：身份卡、欢迎文案、缓存键、公开题库路径、提交版本、本地判定和两个核心云函数都存在大学版硬编码。现有构建脚本也只生成大学版部署产物。

因此本阶段重点不是再次整理文档内容，而是把已经验证的三套内容接入统一运行时。

## 4. 总体架构

采用“单应用、单引擎、多配置”架构：

1. 版本注册表声明可用版本、展示元数据、主题和题库版本；
2. 规范化私有题库保存完整问题与判定数据；
3. 私有算法配置声明可调整的判定参数；
4. 构建脚本校验输入并生成公开题库和后端私有产物；
5. 前端只根据注册表和公开题库渲染；
6. 后端根据提交的版本选择私有题库与算法配置并返回统一结果。

任何版本专属差异必须优先进入数据配置，不在页面中增加散落的版本判断。

## 5. 配置与产物

### 5.1 版本注册表

新增统一版本注册表，至少包含：

- `id`：`high_school`、`university`、`graduate`；
- `enabled`：是否在身份页开放；
- `order`：卡片排序；
- `bank_version`：当前题库版本；
- `title`、`subtitle`、`welcome_copy`、`quiz_label`：界面文案；
- `theme`：主色、浅色背景和强调色；
- `public_bank_file`：公开题库文件名；
- `cache_namespace`：进度缓存命名空间。

身份卡和版本文案全部由注册表生成。以后新增第四版时，只要它符合统一 Schema，前端不需要增加新的身份组件。

### 5.2 私有题库

`data/banks/*.v5.0.0.json` 继续作为三版运行内容的唯一权威来源，包含：

- 版本元数据；
- 16 个标签；
- 20 道题及选项；
- 私有权重和四维向量；
- 核心题映射；
- 彩蛋配置；
- 结果文案与分享文案；
- 使用的 `algorithm_profile`。

前端不得对这些字段做数据修补。缺字段或数据冲突应在构建阶段直接失败。

原始 Markdown 文档保留为需求来源和修订追溯材料，不与规范 JSON 共同承担运行时事实源。Markdown 导入工具只能生成待审查的候选变更；通过校验并合入 `data/banks/` 后，JSON 才能进入构建流程。

### 5.3 算法配置

把以下可调整规则放入私有算法配置，而不是散落在算法代码中：

- 哪些题参与主结果；
- 核心命中的最少有效题数；
- 分差阈值；
- 平分决胜顺序；
- 四维向量的计算与精度；
- 彩蛋题触发方式；
- 第 20 题的角色；
- 算法策略版本。

统一引擎按 `algorithm_profile` 执行。参数调整只改配置；未来若更换完整算法，则新增策略版本，旧题库仍可明确绑定旧策略。

### 5.4 公开与私有构建产物

构建脚本一次处理三个版本，并生成：

- 前端公开题库：题目、选项文字、展示文案和维度名称；
- `get-bank` 使用的公开题库；
- `submit-quiz` 使用的私有题库及算法配置；
- 前端与云函数使用的版本注册表；
- 自动校验结果。

公开题库必须剔除选项权重、核心题映射、目标标签向量及不需要公开的算法参数。

## 6. 前端设计

### 6.1 身份选择

身份页按注册表顺序渲染三个启用卡片。大学版现有视觉语言作为基线，高中版和硕博版只通过主题配置和版本文案形成轻量差异，不复制页面。

选择卡片后设置运行时 `activeVersion`，随后所有页面只从当前版本上下文读取内容。

### 6.2 答题状态

进度键采用版本和题库版本隔离，例如：

`campus-persona:{version}:{bank_version}:progress`

缓存恢复前必须校验：

- 版本与题库版本一致；
- 答案数量和索引合法；
- 题目 ID 属于当前题库；
- 不存在重复答案。

失效缓存应被安全忽略，不能导致 `invalid answer shape` 或跨版本串题。

### 6.3 页面渲染

欢迎页、题目页、分析页和结果页只接收统一视图模型：

- 当前版本展示信息；
- 当前问题与选项；
- 答题进度；
- 主标签结果；
- 四维结果；
- 彩蛋列表；
- 分享文案。

具体题目、标签名和版本专属提示不得出现在 JavaScript 或 HTML 模板常量中。

### 6.4 结果页

三版共用大学版当前结果布局，并动态显示：

- 标签名称、短描述、完整解释；
- 当前版本的四维名称和用户向量；
- 当前版本已触发的彩蛋；
- 当前标签的分享文案；
- 重新测试和返回身份选择入口。

## 7. 判定设计

统一提交结构：

```json
{
  "version": "high_school",
  "bank_version": "5.0.0",
  "answers": [
    { "qid": 1, "selected": 0 }
  ]
}
```

后端处理顺序：

1. 校验版本已启用且题库版本匹配；
2. 加载该版本私有题库和算法配置；
3. 校验每题恰好有一个合法答案；
4. 根据算法配置筛选参与主结果的题；
5. 依次执行核心命中、累计分和四维兜底；
6. 独立收集彩蛋；
7. 返回统一结果结构。

### 7.1 第 20 题约束

第 20 题保留 16 个直觉选项，但默认角色为 `self_perception_only`：

- 不参与核心命中；
- 不参与标签累计分；
- 不参与四维向量；
- 可作为“你的直觉自我认知”附加信息返回；
- 仅改变第 20 题答案时，主标签和四维结果必须保持不变。

该约束从根源上避免结果看起来由最后一题直接决定。若以后产品确认要让第 20 题参与算法，必须通过新的算法配置显式开启，并增加对应回归测试。

### 7.2 统一结果结构

后端返回至少包含：

- `version`、`bank_version`、`algorithm_version`；
- `tag_id`、`tag_name`、短描述、完整描述和关键词；
- `match_method`；
- 四维标签、用户向量和目标向量；
- 彩蛋；
- 第 20 题自我认知信息；
- 分享文案。

前端不根据标签 ID 二次拼接结果。

## 8. 错误处理

- 未知或关闭的版本：返回明确版本错误，身份入口不展示关闭版本；
- 题库版本不匹配：提示刷新题库，不使用旧答案强行提交；
- 答案缺失或越界：定位第一道异常题并返回答题页；
- 本地损坏缓存：忽略并重建，不中断页面；
- 云函数超时或网络失败：分析页停止等待并提供重试、返回答题页两个动作；
- 数据构建失败：输出到具体版本、题目、选项或标签，禁止生成半成品；
- 未知算法策略：后端拒绝启动或提交，不能静默降级；
- 结果文案缺失：构建失败，前端不提供兜底硬编码。

分析页必须有可观测的成功、失败和超时终态，不允许永久停留在“正在生成结果”。

## 9. 兼容与迁移

- 大学版继续使用 `university` 和现有 `5.0.0` 题库语义；
- 旧大学版缓存只在能完整校验时迁移到新命名空间，否则安全丢弃；
- 对大学版固定答案样本保存黄金结果，重构前后标签和四维结果必须一致，第 20 题新约束导致的预期变化单独记录；
- API 在本阶段只接受新统一结构，前端与云函数随同一次发布；
- 构建产物可重复生成，禁止手工修改部署目录中的 JSON。

## 10. 测试设计

### 10.1 数据与构建测试

- 三版注册表 ID 唯一且指向存在的题库；
- 三版题库继续通过现有 16 标签、20 题、选项数、权重、维度、核心题、彩蛋和文案校验；
- 公开产物不包含私有评分字段；
- 构建结果可重复且三个部署目标同步。

### 10.2 算法单元测试

- 三版合法答案均能生成完整结果；
- 核心、累计分、四维兜底和彩蛋路径分别覆盖；
- 维度名称来自当前题库，不再硬编码或乱码；
- 未知版本、版本不匹配、缺题、重复题、越界选项均被拒绝；
- 固定 Q1-Q19、遍历 Q20 的 16 个选项，主标签和四维结果完全不变；
- 大学版黄金样本回归通过。

### 10.3 前端测试

- 身份页生成三个可用卡片；
- 选择不同身份加载对应题库与文案；
- 三个版本缓存互不影响；
- 损坏缓存不会产生 `invalid answer shape`；
- 提交失败或超时可退出分析页并重试；
- 三版结果均能显示对应维度、彩蛋和分享文案；
- 页面源码不存在具体题目和标签硬编码。

### 10.4 验收流程

自动测试通过后，分别完成高中、大学、硕博各一条浏览器端到端流程，并检查移动端布局与大学版风格一致。云函数部署前使用本地模式验证同一批答案在本地和服务端算法中得到一致结果。

## 11. 维护流程

### 更新题目或文案

1. 修改 `data/banks/` 中对应版本的规范 JSON；
2. 如内容来自 Markdown，先用导入工具生成候选变更并人工审查，不直接覆盖权威题库；
3. 运行 Schema、内容和算法冲突校验；
4. 运行统一构建命令生成公开/私有产物；
5. 运行测试后发布。

### 调整算法参数

1. 新建或升级算法配置版本；
2. 让目标题库引用新配置；
3. 增加或更新黄金样本；
4. 构建、测试并发布。

### 新增身份版本

1. 创建符合统一 Schema 的题库；
2. 在版本注册表添加一项；
3. 配置主题和文案；
4. 构建与测试。

正常情况下不需要修改前端页面代码。

## 12. 完成标准

- 三个身份入口在同一应用中可用；
- 三版均完成从选身份到结果分享的完整流程；
- 大学版除明确修正的第 20 题判定外无行为回退；
- 第 20 题变化不改变主标签和四维结果；
- 本地与云端均支持三版；
- 所有题库、算法和前端测试通过；
- 不需要前端手工修补任何题库数据；
- 文档给出题库、算法和新增版本的维护命令与路径。
