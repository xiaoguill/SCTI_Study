# 微信小程序共创工作流 v0.1

> 目的：把 Coze 产出的原始需求、调研、PRD、内容资料和开发参考，转化为可讨论、可验证、可开发、可审查的微信小程序方案。它是一套判断框架，不是把某个项目的页面、题库或技术选型复制到下一个项目。

## 1. 范围与原则

本工作流当前只服务微信小程序。它涵盖从需求建立、网页 Demo 验证、原生小程序实现、代码审查、微信开发者工具验证，到本地/云端上线准备的协作方式。

它不预设题库、人格测试、算法、人物形象、云开发或某一种前端框架。只有当项目目标需要时，才引入对应能力。

工作流由“不确定性”驱动：先找出目前最影响项目成败、但尚未被证实的判断，再用成本最低的验证物降低不确定性。它不是所有项目都必须机械走完同一张清单。

## 2. 从 Coze 材料提取的需求建立方法

这批 Coze 材料呈现的不是单纯的文档堆叠，而是一种“由结果反推、由证据补全、由约束落地”的产品思考方式。

### 2.1 先定义用户最终拿到什么，再反推中间系统

调研报告先识别用户为什么愿意完成、为什么愿意分享；PRD 再把它变成产品价值、用户旅程和结果页；题目与算法文档随后反推每个输入如何支撑结果；开发规则最后把这些体验要求落到数据、接口和运行环境。

这是一种结果先行的逆向设计：

`用户愿意获得与分享的结果 → 形成结果所需的信息 → 用户愿意完成的交互 → 承载交互的数据与技术 → 可验证的交付证据`

未来面对任意小程序时，首先应回答“用户完成后带走什么、有何行动或情绪变化”，而不是先问要做几页、用什么框架。

### 2.2 调研不是照抄案例，而是抽取可迁移机制

调研材料会从外部案例中提炼机制，例如节奏、选择负担、场景化、结果命名、分享动机和群体适配；然后再根据项目用户与目标重新组合，而不是复制案例中的题目、文案或视觉。

未来我会把调研结论拆成三类：

- 已被事实或平台文档支持的约束；
- 值得在本项目验证的产品假设；
- 仅供灵感参考的案例表达。

这样“参考某个爆款”不会被误解为“复制某个爆款”。

### 2.3 用多个视角补全同一个产品模型

Coze 的文档分别从用户分群、内容与结果、交互流程、算法/数据、技术架构、运营指标、风险与上线等角度描述同一个产品。未来我会将这些视角统一到一个需求模型中：

- **结果与价值**：用户为何使用、完成后获得什么、成功如何衡量；
- **用户与场景**：目标人群、具体发生地点、表达尺度与敏感边界；
- **体验与交互**：核心旅程、页面状态、节奏、视觉与分享；
- **内容与业务规则**：文案、商品、题目、表单、任务、计算或推荐规则；
- **数据与变化边界**：哪些是稳定骨架，哪些内容、策略或资源将经常更新；
- **平台与交付**：微信能力、开发者工具、云端、本地调试、合规、性能与上线。

任何一个视角缺失时，我会指出缺口，而不是自行假定答案。

### 2.4 共性骨架与人群/版本差异分开设计

材料中同时存在统一算法框架与不同用户群体的场景表达。这说明复用的重点不是让所有版本看起来一样，而是识别哪些机制应统一，哪些必须随用户变化。

未来会优先把“稳定的体验骨架、数据接口、校验方式”做成可复用能力；把“人群语言、内容、规则参数、视觉资源、运营策略”留在项目配置或内容层。是否配置化由变化频率和维护成本决定，不为配置而配置。

### 2.5 产品承诺必须能追溯到实现与验收

Coze 材料把结果页承诺、内容设计、算法逻辑、JSON 数据结构、API、性能与上线清单连接起来。未来每项关键承诺都应能回答三个问题：

1. 它在用户体验中如何出现？
2. 它依赖哪些内容、规则或技术实现？
3. 用什么证据证明它真的成立？

这使“需求文档”不止是描述，而成为后续 Demo、开发和审查的验收依据。

## 3. Coze → Codex 的需求转化协议

当用户提供 Coze 生成的文件时，我先建立“来源地图”，而不是立即编码。每条材料会标记为：

| 类别 | 含义 | 默认处理 |
|---|---|---|
| 明确目标 | 用户已确认的价值、范围、受众、验收要求 | 必须保留 |
| 业务数据 | 内容、规则、素材、命名、计算逻辑 | 校验完整性、冲突与可维护性 |
| 研究假设 | 调研结论、行业经验、指标参考 | 说明证据等级，必要时验证 |
| 实现建议 | 框架、云端、接口、目录、部署方案 | 作为候选方案，不自动执行 |
| 平台事实 | 微信能力、审核、隐私、性能与安全限制 | 作为硬边界 |
| 未决问题 | 文档遗漏、相互矛盾、影响成本或体验的选择 | 明确列出并请求决定 |

产出是一份“需求建立摘要”：保留目标、关键假设、关键约束、最小验证物、风险与待决项。它只解释目前如何理解项目，不假装替用户做了尚未确认的决策。

## 4. 验证物选择：先验证什么，就先做什么

我会根据最大的未知选择最小验证物：

| 最大未知 | 优先验证物 |
|---|---|
| 用户是否需要、是否愿意传播 | 调研摘要、价值主张、分享结果样例 |
| 页面风格、信息层级、角色表现 | 2–3 个独立 HTML Demo 或视觉样张 |
| 用户是否能顺畅完成关键动作 | 可点击原型或局部原生页面 |
| 内容/规则是否能产生可信结果 | 数据模型、样例推演、自动校验 |
| 微信能力或本地/云端边界 | 最小技术验证、开发者工具编译与运行 |
| 发布是否可行 | 真机、审核材料、云环境与回归清单 |

只有已确认的判断才进入正式工程化。Demo 是决策工具，不应因为“已经做了页面”就被视为正式功能。

## 5. 公开建议与决策权

用户拥有产品取舍与最终发布权。只要我认为现有方案存在更合适的替代，我必须先发出可审阅的建议，内容包含：

- 原方案及其来源；
- 建议方案；
- 依据与预期收益；
- 对体验、成本、维护、上线的影响；
- 不采用建议时的可行路径。

未经确认，我不得把“我的优化建议”当成已决定的需求。

唯一可以直接处理的是不改变产品意图、页面体验、数据含义、架构选择或长期维护成本的细节性实现；即使如此，交付时也应说明。

## 6. 冲突处理与默认优先级

当材料相互矛盾时，默认优先级为：

`用户当前明确指令 > 微信平台与合规事实 > 已验证的项目事实 > 用户已确认的 PRD 决策 > 业务数据与算法资料 > 调研报告 > 开发规则参考 > Codex 优化建议`

这条顺序的作用是避免把“研究中的经验值”误当作强制需求，也避免把“某一项目的开发规则”误当作所有项目的技术标准。用户可以在任一项目中显式覆盖此顺序。

## 7. 工程化与验证边界

项目进入开发后，我负责将已确认内容转化为清晰的模块边界，并用相应验证证明它们成立：

- 变化频繁且不涉及私密逻辑的内容，优先从数据或配置读取；
- 涉及权限、隐私、私有算法、支付或服务端可信性的部分，明确前后端边界；
- 页面不硬编码本应由内容模型提供的数据；
- 每项关键规则有自动校验或样例推演；
- 每项关键用户流程有代码审查、运行检查与微信开发者工具验证；
- 本地调试、云端配置、真机发布是不同状态，必须分别说明是否已完成。

## 8. 未来启动方式

启动新项目时，用户可直接表达：

> 启动微信小程序共创工作流：<一句话目标>。以下是 Coze 产出的需求/调研/参考文档：<文件>。当前优先验证 <视觉 / 内容规则 / 交互 / 技术 / 上线>。

若没有指定优先验证项，我会先指出当前最大不确定性并说明为什么建议先验证它；不会直接把项目带入编码阶段。

## 9. v0.1 的验证与 Skill 演进

本文件是当前唯一方法论来源。下一个真实微信小程序将完整试跑该工作流，并记录：哪些判断稳定有效、哪些提问无效、哪些验证物成本过高、哪些平台步骤必须提前。

经过至少一个真实项目验证后，再把反复成立的动作封装成 Codex Skill。届时 Skill 仅作为执行器，始终以本工作流及用户当前指令为准，不得反向绑死方法论。
