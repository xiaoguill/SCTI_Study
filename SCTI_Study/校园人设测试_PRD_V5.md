# 校园人设测试 · 产品需求文档 PRD V5

> 版本：V5.0 | 状态：完整需求定义 | 适用范围：微信小程序 + QQ小程序
> 核心设计原则：精准定位 → 惊喜共鸣 → 自发传播
> 技术路线：前端 + 云开发（Serverless），支持动态题库与数据统计

---

## 一、产品概述

### 1.1 产品定位

**校园人设测试**——面向高中、大学、硕博三个学生群体的趣味人格测试小程序。通过轻松有趣的场景化题目和"隐性身份探测"算法，帮助用户发现"你是哪种学生"，生成可分享的专属人设标签，驱动社交传播。

**产品本质**：纯娱乐工具，不涉及付费，核心目标是"做完想分享"。

### 1.2 产品核心价值

| 维度 | 描述 |
|---|---|
| 用户价值 | 用 3-5 分钟得到一个精准、有趣、有共鸣的"校园人设标签" |
| 传播价值 | 结果页 + 分享海报设计驱动自发分享，形成社交裂变 |
| 情感价值 | 标签命名采用 SBTI 式抽象隐喻，让用户"会心一笑"——"这说的不就是我吗？" |
| 惊喜价值 | "隐性身份探测"算法让结果出人意料——用户不知道哪些题目在定位自己 |

### 1.3 V2 → V5 核心变化

| 维度 | V2 | V5 |
|---|---|---|
| 标签数量 | 高中12 + 大学12 + 硕博10 | 高中16 + 大学16 + 硕博16（共48种） |
| 题目数量 | 高中12 + 大学12 + 硕博10 | 三套均为20题（共60题） |
| 标签命名 | 直白（"热血冲刺手""六边形战士"） | SBTI 式抽象（"题海纺织工""绩点纺织工""论文纺织工"） |
| 身份探测 | 显性（选 A 就是某类型） | 隐性（身份通过多题行为组合"浮现"） |
| 算法 | 双层（核心匹配 + 维度兜底） | 三层（核心匹配 + 得分累积 + 四维度兜底） |
| 题目风格 | 正经偏多 | 正经 50% + 魔幻 30% + 无厘头 20% |
| 结果页 | 仅主标签 | 主标签 + 四维度雷达图 + 趣味彩蛋（3-4个） |
| 隐性维度 | 无 | 每套6个维度，每个分散在4-5道不同场景中 |
| 后端能力 | 无（纯前端） | 云开发后端（动态题库 + 用户记录 + 数据统计 + 服务端海报） |

### 1.4 核心指标目标

| 指标 | 目标值 | 说明 |
|---|---|---|
| 完赛率 | ≥ 85% | 20 题节奏设计确保用户不弃坑 |
| 分享率 | ≥ 20% | 结果页设计驱动自发分享 |
| 人均做题时间 | 3-5 分钟 | 题目量适中，阅读+选择 |
| 分享回流率 | ≥ 5% | 分享海报含小程序码，驱动回流 |
| DAU | 持续增长 | 通过分享裂变 + 版本迭代拉动 |

## 二、目标用户与分群设计

### 2.1 三群体画像

| 群体 | 年龄段 | 核心生活场景 | 主要关注点 | 敏感话题处理 |
|---|---|---|---|---|
| 高中生 | 15-18 | 课堂、自习室、宿舍、家庭 | 高考、成绩、同学关系、师生互动 | 恋爱→弱化为友情/追星；手机→弱化为课间偷看 |
| 大学生 | 18-22 | 课堂、图书馆、宿舍、社团、校外 | 绩点、社团、恋爱、实习、考研、社交 | 基本无限制，避免过于负面或争议性内容 |
| 硕博 | 22-30 | 实验室、导师办公室、学术会议、租房 | 论文、导师关系、毕业、学术社交、就业 | 导师→幽默化解；薪资→自嘲式表达 |

### 2.2 尺度对照表

| 维度 | 高中版表达 | 大学版表达 | 硕博版表达 |
|---|---|---|---|
| 恋爱/情感 | ❌不直接出现，用"友情/追星/偶像"替代 | ✅"恋爱脑患者"可以直接写 | ✅用"学术恋爱"隐喻（对课题的感情） |
| 手机/娱乐 | 弱化为"课间偷偷看""晚自习走神" | ✅"刷手机到凌晨""追剧"正常写 | ✅"刷学术推特摸鱼""刷论文vs刷视频" |
| 叛逆/不服从 | 弱化为"有自己的想法" | ✅"逃课""摆烂"可以写 | ✅"不想开组会""想退学"自嘲式表达 |
| 核心焦虑 | 月考/期中考/高考/排名 | 绩点/社团/同辈/未来迷茫 | 论文/毕业/导师关系/就业 |
| 时间维度 | 更短视（当下），未来规划弱 | 有中期规划（考研/就业） | 有长远打算（学术/职业） |
| 社交圈 | 以班级/年级为主 | 社团/室友/跨院系 | 学术圈/会议/跨校 |

#### 3.2.4 算法计算模块

**计算方式**：前端实时计算 + 后端二次校验（可选）

前端在用户答完最后一题时立即计算结果，保证即时反馈。后端在收到答题数据后可进行二次校验，用于数据统计和防作弊。

**三层算法流程**：

```
用户答题完成
    ↓
第一层：核心定选题精确匹配
  遍历 16 种标签，检查每种的核心定选题是否全部命中
  命中 → 直接返回结果（matchMethod = 'core'）
    ↓ (无精确命中)
第二层：得分累积取最高
  累加 20 题的 0/1/2 权重得分
  取得分最高者
  若最高分 - 次高分 ≥ 3 → 直接判定（matchMethod = 'score'）
    ↓ (优势 < 3 分 or 并列)
第三层：四维度兜底
  计算用户四维度实际得分向量
  与 16 种标签的标准向量计算曼哈顿距离
  取距离最小者（matchMethod = 'dimension'）
```

**关键约束**：
- 算法确定性：相同输入 → 相同输出，无随机因素
- 前端计算量极小（20题 × 16类型 = 320 次得分累加），毫秒级完成

#### 3.2.6 用户系统

**登录方式**：
- 微信小程序：静默登录（`wx.login` 获取 code → 后端换取 openid）
- QQ 小程序：静默登录（`qq.login` 获取 code → 后端换取 openid）
- 无需用户手动授权，无需获取手机号等敏感信息

**用户数据**：
- 用户标识：openid（微信）/ openid（QQ）
- 用户信息：仅存储平台类型、注册时间、最近登录时间
- 不收集昵称、头像、手机号等个人信息

**测试记录**：
- 每次测试完成后，后端保存一条测试记录
- 记录内容：版本类型、答题选择、匹配结果、匹配方式、耗时
- 用户可在欢迎页查看最近一次结果
- 历史记录列表页（P2，可后期迭代）

#### 3.2.7 动态题库管理

**设计目标**：题库数据存储在云端数据库，后端提供接口动态拉取，无需小程序发版即可更新题目内容。

**管理方式**：
- 通过云开发控制台或后台管理页面维护题库数据
- 题库数据包含版本号，客户端拉取时对比本地缓存版本
- 版本不一致时自动更新缓存

**适用场景**：
- 修复题目错别字
- 调整权重参数
- 新增节日限定题目
- A/B 测试不同题目版本

## 五、统一算法框架

### 5.1 三层算法架构

三套版本共用同一算法框架，差异仅在数据层（标签库、题库、权重矩阵、四维度标准向量）。

```
┌─────────────────────────────────────────────┐
│                 用户答题                      │
│           （20 道题，每题选 1 个选项）          │
└──────────────┬──────────────────────────────┘
               ↓
┌─────────────────────────────────────────────┐
│    第一层：核心定选题精确匹配                  │
│    每种人设有 2-3 道"核心定选题"               │
│    如果某类型的核心题全部命中 → 直接出结果      │
└──────────────┬──────────────────────────────┘
               ↓ (无精确命中)
┌─────────────────────────────────────────────┐
│    第二层：得分累积取最高                      │
│    每个选项对 16 种类型各有 0/1/2 的得分权重    │
│    若最高分 ≥ 次高分 3 分 → 直接判定           │
└──────────────┬──────────────────────────────┘
               ↓ (得分最高者 < 3 分优势 or 并列)
┌─────────────────────────────────────────────┐
│    第三层：四维度兜底                          │
│    曼哈顿距离最小者胜出                        │
└─────────────────────────────────────────────┘
```

### 5.2 第一层：核心定选题精确匹配

每种人设指定 2-3 道"核心定选题"，分散在不同主题场景中，用户不会意识到关联。

**示例**（硕博版 G13 白大褂战士）：
- 核心题1：Q3 选 B（微信步数 15000）→ 表面是步数问题
- 核心题2：Q7 选 B（暑假在医院值班）→ 表面是暑假安排
- 核心题3：Q17 选 B（毕业后想进三甲）→ 表面是毕业打算
- 三题组合精确指向规培医学生

### 5.3 第二层：得分累积

| 分值 | 含义 |
|---|---|
| 2 | 强指向——核心信号 |
| 1 | 弱指向——弱关联 |
| 0 | 无关 |

数据量：每版 20题 × 4选项 × 16类型 = 1280 个权重值，三版共 3840 个。

### 5.4 第三层：四维度兜底

| 维度 | 高中版含义 | 大学版含义 | 硕博版含义 |
|---|---|---|---|
| D1 | 学习投入度 | 学业投入度 | 学术投入度 |
| D2 | 社交活跃度 | 社交活跃度 | 社交活跃度 |
| D3 | 自律执行力 | 自律执行力 | 自律执行力 |
| D4 | 兴趣开放性 | 探索开放性 | 探索开放性 |

曼哈顿距离公式：`Distance = |d1-t1| + |d2-t2| + |d3-t3| + |d4-t4|`

### 5.5 算法确定性保证

- 第一层遍历顺序固定（编号从小到大），首个全命中的即为结果
- 第二层排序固定（得分降序，同分取编号小者）
- 第三层曼哈顿距离确定性，同距离取编号小者
- **结论**：固定选择 → 固定结果，无随机因素

## 七、分享机制设计

### 7.1 微信分享

**转发卡片**（`onShareAppMessage`）：
- 标题：`我是「{标签名}」{一句话描述} 测测你是哪种？`
- 图片：服务端生成的分享封面（5:4，含标签名 + 一句话 + 小程序码）
- 路径：`/pages/result/index?tagId={tagId}&version={version}`

**朋友圈分享**（`onShareTimeline`）：
- 标题：`我是「{标签名}」，你呢？`

**分享回流**：
- 用户点击分享卡片 → 展示分享者结果页（只读）
- 底部 CTA：`测测你是哪种？` → 进入欢迎页

### 7.2 QQ 分享

- 转发到好友/群：通过 `onShareAppMessage`（QQ API 类似微信）
- 分享到 QQ 空间：通过 `qq.shareToQzone` API
- QQ 空间分享图片尺寸 1:1

### 7.3 服务端海报生成

**技术方案**：后端使用 Node.js Canvas（node-canvas / sharp）渲染海报图片，前端直接展示/保存。

**海报内容**：

```
┌────────────────────────┐
│  校园人设测试           │
│                        │
│  我是「{标签名}」       │
│  {一句话描述}           │
│                        │
│  [四维度雷达图(小)]     │
│  {四维度关键词}         │
│                        │
│  ┌────────┐            │
│  │小程序码 │            │
│  └────────┘            │
│  扫码测测你是哪种？     │
└────────────────────────┘
```

**海报尺寸**：
- 微信分享封面：750×600px（5:4）
- 保存海报：750×1334px
- QQ 空间分享：750×750px（1:1）

## 十四、风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 审核不通过 | 延迟上线 | 提前了解审核规则，避免敏感词 |
| 分享率不达标 | 传播效果差 | 优化结果页文案，增加"梗点"密度 |

## 附录 H：错误处理与边界情况

### H.1 前端错误处理

| 场景 | 处理方式 | 用户提示 |
|---|---|---|

| 结果页异常 | 重新计算结果 | 自动跳转重新计算 |

### H.2 后端错误处理

| 场景 | 处理方式 |
|---|---|
| 题库版本不存在 | 返回最新可用版本 |
| 答题数据不完整 | 返回错误码，前端提示重新答题 |
| 频率限制触发 | 返回 429，前端提示"稍后再试" |
