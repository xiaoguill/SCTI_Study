# 校园人设测试 · 小程序开发规则与技术规范

> 版本：V5.0 | 状态：技术规范定义 | 适用范围：微信小程序 + QQ小程序
> 本文档面向个人独立开发者，提供完整的前后端开发指导

---

## 一、技术选型与架构总览

### 1.1 技术栈推荐

| 层级 | 推荐方案 | 备选方案 | 选型理由 |
|---|---|---|---|
| 前端框架 | **uni-app (Vue3 + Composition API)** | 原生小程序 / Taro | 一套代码编译微信+QQ双端，社区生态成熟，HBuilderX 开发效率高 |
| 状态管理 | **Pinia** | Vuex | 轻量、TypeScript 友好，适合中小型项目 |
| 样式方案 | **SCSS + rpx 适配** | Tailwind CSS (miniprogram) | rpx 天然适配多端屏幕，SCSS 提高复用性 |
| 图表渲染 | **Canvas 2D API 自绘** | uCharts / echarts | 仅需雷达图，自绘最轻量，无额外依赖 |
| 后端方案 | **微信云开发（CloudBase）** | 腾讯云 SCF / 自建 Node.js | 免运维、与小程序深度集成、按量计费适合小项目 |
| 云函数运行时 | **Node.js 18+** | — | 前后端语言统一，降低维护成本 |
| 数据库 | **云数据库（文档型/MongoDB-like）** | 腾讯云 TDSQL / MySQL | 灵活 schema、免运维、天然适配 JSON 数据 |
| 文件存储 | **云存储** | COS | 存放海报图片、静态资源 |
| 海报渲染 | **node-canvas / sharp（云函数中）** | 客户端 Canvas | 服务端渲染质量高、性能好、可缓存复用 |
| 构建工具 | **HBuilderX / uni-app CLI** | VSCode + CLI | HBuilderX 一键运行多端 |

### 1.2 为什么选微信云开发而非自建后端

| 维度 | 微信云开发 | 自建后端（Node.js + MySQL） |
|---|---|---|
| 运维成本 | 零运维，自动扩缩容 | 需自行管理服务器、数据库、SSL |
| 开发效率 | 前后端一体，部署一键完成 | 需分别部署前后端 |
| 成本 | 按量计费，低流量几乎免费 | 服务器最低成本 ~50元/月 |
| 与小程序集成 | 原生支持，免域名配置 | 需配置域名、HTTPS、白名单 |
| 适用场景 | 个人开发者、小体量应用 | 大规模、需要复杂后端逻辑 |
| 限制 | 不能访问外部网络（需开通） | 无限制 |

**结论**：个人独立开发者 + 小体量娱乐小程序 → 微信云开发是最佳选择。

## 四、API 接口设计规范

### 4.1 通用规范

**请求格式**：
- 所有请求通过 `wx.cloud.callFunction` / `qq.cloud.callFunction` 调用
- 请求参数通过 `data` 字段传入
- 统一返回格式如下：

```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

**错误码定义**：

| 错误码 | 含义 | 前端处理 |
|---|---|---|
| 0 | 成功 | 正常处理 |
| 401 | 未登录 / token 过期 | 自动重新登录 |
| 403 | 权限不足 | 提示用户 |
| 404 | 数据不存在 | 提示并返回上一页 |
| 429 | 请求过于频繁 | 提示"稍后再试" |
| 500 | 服务端错误 | 提示"系统繁忙" |

### 4.2 用户登录接口

**云函数名**：`user-login`

**请求参数**：
```json
{
  "action": "login",
  "platform": "wechat | qq",
  "code": "wx.login() 获取的 code"
}
```

**响应数据**：
```json
{
  "code": 0,
  "data": {
    "token": "jwt_token_xxx",
    "user_id": "xxx",
    "is_new_user": true,
    "last_test": {
      "version": "university",
      "tag_id": "U6",
      "tag_name": "DDL爆破手",
      "created_at": "2026-07-15T10:00:00+08:00"
    }
  }
}
```

**处理逻辑**：
1. 用 code 调用微信/QQ接口换取 openid
2. 查询 users 表是否存在该 openid
3. 不存在则创建新用户记录
4. 生成 JWT token（有效期 7 天）
5. 返回 token 和用户信息

**关键设计**：
- **不返回 `scores` 字段**：客户端仅获得选项文本，权重数据保留在服务端
- **版本号对比**：客户端缓存题库版本号，不一致时才拉取完整数据
- **`core_questions` 下发**：客户端需要核心定选题数据来进行第一层匹配（即时反馈）
- **`easter_egg_mapping` 下发**：客户端需要彩蛋映射来展示趣味结果

> **安全权衡说明**：`core_questions` 和 `dimensions` 下发到客户端存在一定泄露风险，但为了实现即时结果反馈（无需等待网络请求），这是必要的折中。后端在 `submit-quiz` 时会进行二次校验。后续可通过混淆核心题号来增加泄露难度。

## 五、三层算法实现规范

### 5.1 算法输入输出定义

**输入**：
```json
{
  "version": "university",
  "answers": [
    { "qid": 1, "selected": 0 },
    { "qid": 2, "selected": 2 }
  ],
  "question_bank": {
    "tags": [ ... ],
    "questions": [ ... ]
  }
}
```

**输出**：
```json
{
  "tag_id": "U6",
  "tag_name": "DDL爆破手",
  "match_method": "core | score | dimension",
  "scores_ranking": [
    { "tag_id": "U6", "score": 18 },
    { "tag_id": "U14", "score": 14 }
  ],
  "dimensions": {
    "user_vector": [3.2, 2.1, 1.8, 3.5],
    "target_vector": [3, 2, 1, 3],
    "manhattan_distance": 0.7
  }
}
```

### 5.2 第一层：核心定选题精确匹配

**算法逻辑**：

```
function layer1_coreMatch(answers, tags):
    for tag in tags (按 id 升序):
        if tag.core_questions is empty:
            continue
        allMatched = true
        for coreQ in tag.core_questions:
            userAnswer = answers.find(qid == coreQ.qid)
            if userAnswer is null OR userAnswer.selected != coreQ.answer_index:
                allMatched = false
                break
        if allMatched:
            return { tag_id: tag.id, match_method: "core" }
    return null  // 无精确命中
```

**关键约束**：
- 遍历顺序固定（tag id 升序），保证确定性
- 所有核心题必须全部命中才算匹配成功
- 若多个类型同时全命中（理论不应发生），取 id 小者

### 5.3 第二层：得分累积

**算法逻辑**：

```
function layer2_scoreAccumulate(answers, questions, tags):
    scores = {}
    for tag in tags:
        scores[tag.id] = 0
    
    for answer in answers:
        question = questions.find(id == answer.qid)
        option = question.options[answer.selected]
        for tag_id in scores.keys():
            scores[tag_id] += option.scores[tag_id] || 0
    
    // 排序：得分降序，同分按 tag_id 升序
    sorted = scores.entries().sort((a, b) => 
        b.score != a.score ? b.score - a.score : a.tag_id.localeCompare(b.tag_id)
    )
    
    if sorted[0].score - sorted[1].score >= 3:
        return { tag_id: sorted[0].tag_id, match_method: "score" }
    
    return null  // 优势不足，进入第三层
```

**关键约束**：
- 未出现在 `option.scores` 中的类型默认得分为 0
- 排序规则：先按得分降序，同分按 tag_id 字典序升序
- 阈值硬编码为 3 分

### 5.4 第三层：四维度兜底

**算法逻辑**：

```
function layer3_dimensionFallback(answers, questions, tags):
    // 1. 计算用户四维度向量
    dimSums = [0, 0, 0, 0]
    count = 0
    for answer in answers:
        question = questions.find(id == answer.qid)
        option = question.options[answer.selected]
        if option.dimensions exists:
            dimSums[0] += option.dimensions[0]
            dimSums[1] += option.dimensions[1]
            dimSums[2] += option.dimensions[2]
            dimSums[3] += option.dimensions[3]
            count++
    
    userVector = dimSums.map(sum => sum / count)
    
    // 2. 计算与每种标签的曼哈顿距离
    minDistance = Infinity
    bestTag = null
    for tag in tags (按 id 升序):
        distance = 0
        for i in 0..3:
            distance += abs(userVector[i] - tag.dimensions[i])
        if distance < minDistance:
            minDistance = distance
            bestTag = tag
    
    return { tag_id: bestTag.id, match_method: "dimension" }
```

**曼哈顿距离公式**：
```
Distance = |d1 - t1| + |d2 - t2| + |d3 - t3| + |d4 - t4|
```

**关键约束**：
- 四维度分值范围 1-5，取 20 题平均值
- 同距离取 tag_id 小者
- 四维度标准向量定义在每个 tag 的 `dimensions` 字段中

### 5.5 算法整体流程

```
function calculateResult(answers, questionBank):
    // 第一层
    coreResult = layer1_coreMatch(answers, questionBank.tags)
    if coreResult != null:
        return coreResult
    
    // 第二层
    scoreResult = layer2_scoreAccumulate(answers, questionBank.questions, questionBank.tags)
    if scoreResult != null:
        return scoreResult
    
    // 第三层
    dimResult = layer3_dimensionFallback(answers, questionBank.questions, questionBank.tags)
    return dimResult
```

### 5.6 前端 vs 后端计算分工

| 计算环节 | 前端 | 后端 |
|---|---|---|
| 第一层核心匹配 | ✅ 即时反馈 | ✅ 二次校验 |
| 第二层得分累积 | ✅（需本地存储权重数据） | ✅ |
| 第三层四维度 | ✅ | ✅ |
| 最终结果 | 以前端计算为准（即时展示） | 以后端校验为准（统计数据） |
| 差异处理 | 如果前后端结果不一致，前端展示以后端返回为准 | 后端结果写入数据库 |

**权重数据的客户端存储策略**：
- 客户端通过 `get-bank` 接口获取题库时，虽然主接口不返回 `scores`，但可提供一个**独立的轻量权重接口**（或在题库中包含简化版权重）
- 或者：客户端在本地硬编码一份权重快照，每次发版时更新
- 推荐方案：权重数据随题库一起下发，但在传输层做简单编码（非加密，仅防止直接阅读）

```
管理员修改题库数据（云开发控制台 / 管理后台）

    ↓
```

### 9.2 客户端缓存策略

```

  1. 读取本地缓存的题库数据和版本号

     - 更新本地缓存
     - 使用新题库
  4. 如果 need_update = false：
     - 直接使用本地缓存
  5. 如果网络失败：
     - 使用本地缓存兜底
     - 提示"已使用离线题库"

```

## 十、安全设计

### 10.1 接口鉴权

```
每个云函数入口统一校验：
  1. 从 event.header 获取 token
  2. 解码 JWT，验证签名和有效期
  3. 提取 user_id
  4. 未通过则返回 { code: 401 }
```

### 10.2 防刷策略

| 接口 | 限制规则 | 实现方式 |
|---|---|---|
| submit-quiz | 同一用户同一版本 5分钟内限 3次 | 查询最近 5 分钟内的提交记录数 |
| gen-poster | 同一用户每分钟限 5次 | 查询最近 1 分钟的生成记录数 |
| user-login | 同一 IP 每分钟限 10次 | 云函数层面限流 |
| get-bank | 无限制（有缓存兜底） | — |

### 10.3 题库保护措施

| 措施 | 说明 |
|---|---|
| 权重数据不直接暴露 | scores 字段通过编码传输，前端需要解码 |
| 核心题号混淆 | 下发的 core_questions 可以做简单映射变换 |
| 服务端二次校验 | 前端计算结果需经后端验证，不一致以后端为准 |
| 定期更新题库 | 可通过动态题库机制定期微调权重，防止逆向 |

### 10.4 数据安全

| 措施 | 说明 |
|---|---|
| openid 加密存储 | AES-256 加密后存入数据库 |
| 传输加密 | 云函数调用自动走 HTTPS |
| 数据隔离 | 用户只能查询自己的数据（通过 user_id 过滤） |
